# Diagnostic Impact Report

## Purpose and API

The Project Owner-owned `/diagnostic-impact` workspace displays a read-only report generated by the backend for a real backend-owned diagnostic session. The API is `GET /api/diagnostic-impact/?session_id=<backend-session-id>`. If `session_id` is omitted, the backend selects the active session or most recently created session. An unknown or unavailable session returns 404. No session identifiers or measurement timestamps are generated by the browser. The report labels ECS target impact separately from RDS and ElastiCache dependency observations.

The frontend uses the shared DCC API client and validates the normalized report response. React displays backend-calculated values and classifications; it does not aggregate task, API-testing, or log mock fixtures into an impact report. The browser never contacts metrics or log providers directly.

## Measurement ownership and phases

`DiagnosticImpactService` in `backend/apps/diagnostics/impact.py` receives normalized resource metrics from the existing metrics service and owns bounded in-memory phase capture and calculation. It does not use boto3, PromQL, LogQL, or provider-native responses.

- **Baseline** is captured by the backend when a session starts, before diagnostic execution begins.
- **During** begins after execution starts. The backend captures an initial sample and then samples every five seconds, up to 60 samples per session. The sampler is stopped when the session becomes terminal. It is bounded, process-local, and independent of frontend polling.
- **Post** is attempted when a session stops, completes, or fails. A metrics failure or unavailable post sample does not change or fail the diagnostic session transition.

For each phase, the report identifies capture status, capture timestamp, metrics source, sample count, and any safe availability detail. These timestamps indicate when DCC read the normalized metric, because the shared metrics contract does not include original provider sample timestamps. During values are averages of available samples; the during peak is the highest sampled current value. Missing measurements remain unavailable and are never substituted with zero. The report can be partial or unknown when a phase/provider is unavailable or not configured. Only `mock`, `cloudwatch`, and `prometheus` source names are exposed; credentials, provider internals, and native responses are not returned.

CloudWatch/Prometheus data is only meaningful for a DCC target if its existing provider mapping resolves that target. In particular, the current CloudWatch provider reports configured ECS service aggregates rather than per-task samples; Prometheus uses the DCC `task_id` label mapping documented in the backend setup guidance. The report does not claim per-task or diagnostic attribution that the selected provider cannot supply.

## Calculations and classification

For each CPU, memory, and network metric, the backend returns baseline, during average, post value, during peak, and absolute/percentage deltas where possible. Absolute delta is `phase value - baseline`. Percentage delta is calculated only when the baseline is non-zero; zero baselines retain a valid absolute difference but have a null percentage. A non-zero difference from a zero baseline cannot be assigned a percentage-based impact classification and yields `unknown` rather than a misleading zero-percent result.

The deterministic **DCC application thresholds** use the largest available absolute percentage change, preferring during comparisons and using post only when there are no comparable during measurements:

| Classification | Largest absolute percentage change |
| --- | --- |
| `none` | 0–5% |
| `low` | >5–15% |
| `moderate` | >15–30% |
| `high` | >30% |
| `unknown` | Insufficient comparable data or a non-zero zero-baseline change |

These are product-specific reporting thresholds, not scientifically universal limits or proof of causality. The report explicitly states that application-level measurement is not scientific causal analysis and does not prove the diagnostic caused an observed change.

## Logs and API testing

The report requests normalized logs for the target task through the existing logs service. Only entries whose `diagnostic_session_id` exactly matches the backend session ID are marked session-correlated. Other target-task logs are shown as contextual only and are not attributed to the diagnostic. If the logs provider is unavailable, the report indicates that state instead of reporting an empty successful result.

API Testing does not currently provide real session-associated execution results. Its report section says `not_provided`; no sample request counts or outcomes are represented as diagnostic data.

## Lifecycle, bounds, and limitations

Session and report state is process-local and is lost when the backend restarts. There is no database, Celery worker, Redis queue, persistence, cross-process coordination, or report history beyond the current backend process. During sampling is limited to one active session and at most 60 samples at five-second intervals. A provider that is not configured or cannot return metrics produces safe unavailable phase data; it does not silently fall back to mock data. Logs and metrics remain independently selected by `DCC_LOGS_PROVIDER` and `DCC_METRICS_PROVIDER`.

The workspace can refresh the report manually. It does not add report polling or streaming. Metrics default to CloudWatch and logs to Loki; the associated endpoints must be configured for real measurements. Explicitly selected mock providers are test/development-only. Tests use mocked provider boundaries and require no AWS account, Prometheus/Loki server, or network access.

This integration is not a complete production observability system. It does not provision or configure CloudWatch, Prometheus, Loki, ECS, or any monitoring infrastructure; it does not add persisted history, API execution, alerting, or scientific causal analysis.

## Dependency observations

The report's `dependencies` section is keyed to the same backend session ID and is calculated from normalized dependency snapshots. It reports baseline, during, and best-effort post phases independently from the ECS target metrics. RDS CPU and database connection values and ElastiCache CPU and memory usage are compared only when both the baseline and the relevant phase measurement are available; peak-during values are shown when present. Missing values remain null/unavailable, and no dependency-specific impact classification is inferred. Dependency deltas do not change the ECS target classification and are not proof that the diagnostic caused a dependency change.

Dependency observations use `DCC_DEPENDENCIES_PROVIDER=cloudwatch` by default (`mock` requires explicit opt-in) and are also available in the separate read-only Dependency Observability workspace via `GET /api/dependencies/`. When a backend diagnostic session is active, the endpoint identifies it as `active_session_observation`; without one, ordinary telemetry is labeled `current_health`. Set `DCC_DEPENDENCY_RESOURCES` to a JSON array of configured IDs (up to 20), with `resource_type`, `resource_id`, optional `engine`, and optional `resource_scope`. RDS uses `db_instance`; ElastiCache supports `cache_cluster` or `replication_group`. CloudWatch uses the configured region and boto3's standard credential chain. It reads RDS CPU, connections, free storage, IOPS, and network metrics and ElastiCache CPU, cache memory, connections, and network metrics. ElastiCache network-byte sums are converted to bytes per second over the 60-second metric period. CloudWatch metric queries do not provide health status, so live status is unknown. Empty, missing, unsupported, or inaccessible metric data remains unavailable; it does not become zero or fail the diagnostic lifecycle. The provider has bounded request timeouts/retries and normalizes permission, throttling, timeout, and other provider errors without exposing raw AWS exceptions. No dependency mutation operations are implemented.
